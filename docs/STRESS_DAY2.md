## 学生の実行方法

既存のwork/をそのまま使用します。通常のWSLターミナルで実行してください。

6種類をまとめて確認するコマンドもあります。開発中は `./rr mock-stress --lite`、最終確認は `./rr mock-stress --full` を使います。基準比の幾何平均を表示する練習用評価で、正式な180秒スループットの点数とは別です。[詳しい使い方・実測時間](MOCK_STRESS.md)を参照してください。既存の `./rr mock` の対象3種類は変わりません。

```bash
./rr check --dataset stress_open_unique
./rr bench --dataset stress_open_unique
./rr check --dataset stress_detour
./rr bench --dataset stress_detour
./rr check --dataset stress_maze_long
./rr bench --dataset stress_maze_long
./rr check --dataset stress_islands_mixed
./rr bench --dataset stress_islands_mixed
```

作業用候補もパスを指定するだけで使用できます。

```bash
./rr check --dataset results/stress_day2/stress_open_unique
./rr bench --dataset results/stress_day2/stress_open_unique
```

benchは基準・自分のプログラムを各5回実行するため、この4種類全体では数分以上かかります。他のベンチマークや重い処理と同時に実行しないでください。全5回正解・制限遵守の中央値を使用します。INCOMPLETEは未完了であり、誤答や0点と解釈せず再測定します。

## 生成・検証・調整

Python 3標準ライブラリだけを使用します。生成先が既に存在する場合は上書きしません。幅・高さは31〜300、問い合わせ数は1〜2,000を受け付けますが、混在分布の構造検査には十分な問い合わせ数が必要です。公開版の確定条件は各metadata.jsonと同梱の結果JSONを参照してください。

```bash
# 少数問い合わせからの自動調整。新しい出力先を指定する。
systemd-run --user --wait --pipe --collect --working-directory="$PWD" \
  /usr/bin/python3 tools/stress_dataset.py tune --output results/stress_day2-retune

# 任意の公開条件で生成する例（配布版そのものの条件はmetadata参照）。
python3 tools/stress_dataset.py generate \
  --output results/my-stress-detour --kind stress_detour \
  --width 181 --height 181 --queries 100 --seed 12345

# 全件の正解検証・制約検査・再生成・SHA-256を記録する。
python3 tools/stress_dataset.py validate \
  --dataset results/my-stress-detour --evidence results/my-stress-detour-evidence

# 正解検証済みの答えから、BFS・双方向BFS・A*の探索セル数を比較する。
python3 tools/stress_search_profile.py \
  --dataset results/my-stress-detour \
  --answers results/my-stress-detour-evidence/answers.txt \
  --output results/my-stress-detour-search.json
```

確定した条件だけを再生成するには、`generate` のkind・width・height・queries・seedをmetadataの `stress_generator` に合わせます。同一生成器・同一条件で3ファイルのバイト一致を検査済みです。将来Pythonの乱数実装等が変わる場合に備え、検証結果にはPython版と生成スクリプトのハッシュも保存します。

追加入力は `.gitattributes` で改行の自動変換を無効化し、Gitから取得した場合も測定時のSHA-256を保ちます。CSVのCRLFは既存の `csv.writer` によるものです。既存データの属性は変更しません。

`tune` は既存の `tools.benchmark.evaluate()` と `run_isolated()` を呼びます。まず24件以下のpilotを測り、基準の実測中央値から問い合わせ数を15秒付近へ調整し、最大4段階で再測定します。問い合わせ数が24または2,000の調整境界に達しても負荷が合わない場合は、幅・高さも31〜300の範囲で調整します。初期サイズは地図構造ごとに変えています。10〜20秒は調整目標であり競技の時間制限ではありません。調整時の60秒停止は運営上の安全停止で、正式な制限ではありません。

測定JSONの `team_id=TRUSTED_REFERENCE_BFS_CALIBRATION_ONLY` は検証用の既存参照BFSです。学生チームA〜Eの改善版や最速版ではありません。COMPLETEかつbaseline/teamの全10回がOKの場合だけ負荷調整に使用します。環境障害時も地図と全件の正解は検証し、性能はPENDINGにします。PENDINGの候補は正式評価には使用しません。

`load_dataset()`によるサイズ・ファイル容量・座標・通行可能セル・metadata・件数の検査に加えて、既存の参照BFSと独立した一次元配列BFSを全件照合します。基準Dijkstraも隔離測定中の全5回で同じ答えを出すことを確認します。連結成分、到達可否、始終点の重複、Manhattanとの差・比、分岐数を記録します。重複率は `1 - distinct/count`、endpoint重複率は始終点を合算した2Q個に対する値です。距離差・比の集計から到達不能を除外し、比ではManhattan=0も除外します。

stress_detourは到達不能を含み、全件の65%以上が「正解−Manhattan ≥ 高さ/2の切り捨て、かつ正解 ≥ Manhattanの2倍」を満たさなければ検証に失敗します。障害物率だけで直接距離を返す誤実装を検出できます。

## 実行器の現状と性能値の扱い

実行器は終了後にcgroupが空になるまで最大200ms待ち、残存時のPID・状態・CPU時間等を記録する修正が既に入っています。待機時間も計測に含みます。猶予後も残存する場合はLEFTOVER_PROCESSESで、成功扱いにはしません。今回、この部分への変更はありません。

AIツール内の制限環境ではユーザーsystemdへの接続が拒否されました。通常WSL側のユーザーサービスでは既存の隔離・128MiB制限を保った測定が可能でした。sudo、制限解除、システム設定変更は使いません。再現しない場合は診断JSONとともに保留し、隔離なしの値で代用しないでください。

この公開データによる負荷は実装・環境によって変わります。特に開放地図は正しい直接距離判定を持つ実装で非常に速くなる可能性があります。最速チームのコードは今回の比較対象に含まれていないため、そのコードでも固定コストを十分超えることまでは確認していません。相対比較は同じマシン・同じ入力ハッシュ・同じ時期の5回測定で行ってください。

## 180秒スループット案（設計のみ・未採用）

技術的には、外側の運営プログラムが同じ提出プログラムを地図ごとに起動することで、現行の「1実行＝1地図」を維持できます。各実行は既存ランナーの新しいcgroup・namespaceで128MiB、swapなしとし、前処理・読み込み・出力・終了後の後始末も含めます。外側の180秒は追加種目の運営予算です。既存競技の1実行に時間制限を追加しません。

成立させるには、少なくとも次を事前に決める必要があります。

| 論点 | 設計候補と注意点 |
|---|---|
| 正解と枚数 | 正解は事前に参照解で準備し、地図ごとに全問い合わせの出力を照合してから1枚と数える。先頭の正解問い合わせだけを部分加算しない。 |
| 難易度 | 全チームに同一の順序・同一バイトの地図列を使う。構造4種類を層化した小ラウンド単位で揃え、難易度別の完了数も併記する。異なる難易度のランダム地図を単純に1枚換算すると不公平。順序効果が残るため複数回の順序交替も検討する。 |
| 起動固定コスト | 地図が軽すぎるとPython・bubblewrap・入力コピー・cgroup生成の速度を比べる競技になる。代表的な高速実装で処理時間と起動オーバーヘッドの比を実測してから負荷を選ぶ。永続ワーカーは入力契約・隔離条件を変えるためこの案では使わない。 |
| 180秒の境界 | 外側の単調時計で終了時刻を管理し、残り予算を既存ランナーの運営停止へ渡す設計は可能。予算内に出力と後始末まで完了した地図を対象とする。最後の未完了は枚数に加えず、誤答扱いにしない。 |
| 誤答・制限違反 | 例：初回違反でその試行を停止し、直前までの連続正解枚数と違反理由を表示する。間違えやすい地図を高速に飛ばす戦略を許すか否かを先に明示する。OOM・不正出力・実行失敗の扱いも同時に固定する。 |
| 運営停止・環境障害 | 開始前に基準の完走を確認する。基準異常、隔離障害、計測中の運営停止は試行全体をINCOMPLETEとして再実行し、0枚や失格に変換しない。LEFTOVER_PROCESSESは既存診断で環境要因か提出側の残存かを調査する。 |
| 判定時間 | 外側180秒へ入力準備・結果照合を含めるか、提出処理時間の合計を180秒にするかで競技が変わる。壁時計180秒案なら準備・判定も全チームで同じ処理に固定し、運営負荷を単独稼働で抑える。 |
| 現行採点との関係 | 公式は従来の各データ5回中央値のまま。追加チャレンジは別表の参考記録とし、既存P・総合点へ合算しない。正しさを重視しつつ複数条件への安定した高速化を体験できる。 |

メリットは幅広い地図を処理し続ける実用的な速さが見えることです。デメリットは起動・判定コスト、境界時刻、地図の順序と難易度差に結果が左右され、中央値方式より運営条件の統制が難しいことです。現段階では設計検討までとし、新しい実行器・スコア計算器・正式ルールは追加しません。
